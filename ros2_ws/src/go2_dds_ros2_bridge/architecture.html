GO2 DDS / ROS2 Fusion Architecture

This page shows how the physical GO2, the simulate_python runtime, and the ROS2 bridge package fit together in the current fusion setup. The main paths are the raw DDS transport, the bridge nodes that translate DDS into ROS2 topics, the KISS-ICP odometry branch, and the local EKF that owns the runtime frame tree.

Recommended entry point: ekf_fusion.launch.py
Raw DDS side: run_mode plus optional dds_domain_id / dds_interface
Raw topics: rt/odom, rt/utlidar/cloud
ROS2 outputs: /odom, /utlidar/time_corrected/cloud, /kiss/odom, /odometry/filtered
KISS input: accumulated clouds, header-shifted point time, periodic reset at 100 registrations
Physical robot, onboard sensors, Ethernet link
simulate_python scripts and MuJoCo-side runtime
go2_dds_ros2_bridge ROS2 executables
ROS2 topics consumed by RViz, SLAM, or other ROS tools
TF ownership in the current fusion launch

1. End-to-End Map

The package does not import simulate_python. Both sides stay decoupled and meet only through shared DDS topics. In the recommended launch, the bridge nodes publish ROS topics, the static publisher owns the LiDAR extrinsic, and the EKF publishes the only dynamic odometry transform.

2. Hardware Path: GO2 to ROS2

On hardware, the ROS2 bridge listens to the same Unitree DDS traffic the robot publishes on the wired Ethernet path.

What matters here

  • The raw DDS side still has hardware defaults, but the fusion launch can override them with dds_domain_id and dds_interface.
  • clock_offset_bridge is the LiDAR cleanup step. It aligns timestamps to local ROS time before anything downstream uses the cloud.
  • odom_bridge is the low-friction path for robot odometry into standard ROS2 tools.
  • In the current fusion runtime, base_link -> utlidar_lidar comes from static_transform_publisher, not from clock_offset_bridge.

3. Simulation Path: simulate_python to ROS2

In simulation, the contract is still DDS. The ROS2 bridge only cares that the expected topics exist; it does not need a Python import from the simulator.

Where the script interaction happens

  • unitree_mujoco.py and the control scripts initialize Unitree DDS channels for the simulator side.
  • GO2HardwareEnvironment creates EstimatedOdometryPublisher when velocity control is active.
  • That publisher writes DDS rt/odom, which the ROS2 odom_bridge can consume exactly like hardware odometry.
  • The ROS domain is still selected separately with ROS_DOMAIN_ID; the bridge DDS side is controlled by run_mode and optional launch overrides.
  • This symmetry is the key design choice: same launch, same ROS2 outputs, different DDS producer.

4. Fusion Inputs and EKF Split

KISS-ICP deliberately subscribes to the corrected ROS2 cloud instead of raw DDS so it can reuse the timestamp fix from one place. The EKF then takes pose from /kiss/odom and twist from /odom. That is the current runtime split configured in ekf_localization.yaml.

Why this split is useful

  • The timestamp correction happens once in clock_offset_bridge, and both KISS and other ROS tools reuse the corrected cloud.
  • kiss_odom_node stays focused on scan registration rather than DDS transport details.
  • The node accumulates multiple incoming clouds before each KISS registration because single-message registration was too unstable on the GO2 stream.
  • The published KISS pose is expressed at the base_link origin in the odom frame, so the EKF can fuse it directly.
  • --reset-after-registrations bounds KISS map history while keeping the published pose continuous.
  • If you disable KISS-ICP, the rest of the bridge still works, but the fused launch loses its pose measurement source.

5. TF Ownership in the Fusion Launch

The current fusion launch has a single runtime TF chain: odom -> base_link -> utlidar_lidar. Raw estimator odometry and KISS remain ROS topics that feed the filter; they do not own extra TF branches.

Reading the frame tree

  • odom -> base_link comes from robot_localization/ekf_node.
  • base_link -> utlidar_lidar comes from static_transform_publisher.
  • odom_bridge does not publish TF in the fusion launch.
  • kiss_odom_node does not publish TF in the fusion launch.
  • clock_offset_bridge can still publish TF when run standalone, but the launch disables it so TF ownership stays unambiguous.
