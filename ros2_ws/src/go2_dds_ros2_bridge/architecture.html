GO2 DDS / ROS2 FAST-LIO Architecture

This page reflects the current bridge design after removing the KISS-ICP and EKF fusion path. The active launch is now a direct DDS-to-FAST-LIO pipeline with optional rolling 2D occupancy mapping. Hardware and simulate_python remain symmetric at the transport layer: both publish the same DDS contract, and the bridge turns that into corrected ROS topics, static transforms, FAST-LIO inputs, and an optional occupancy grid.

1. End-to-End Runtime

The current launch is narrower and more explicit than the old fusion stack: correct the LiDAR clock, bridge the IMU, publish fixed transforms, run FAST-LIO, and optionally derive a rolling occupancy grid from the registered cloud.

The package still ships standalone utilities such as odom_bridge, but the main launch no longer routes odometry through KISS-ICP or robot_localization.

What changed

  • The recommended entry point is now fast_lio.launch.py, not a fusion launch.
  • KISS-ICP is no longer installed or documented as part of the active package path.
  • robot_localization is no longer part of the package runtime dependency set.
  • Occupancy mapping is now the downstream consumer of the FAST-LIO registered cloud inside this package.
  • The design is closer to a pure transport-and-mapping stack: bridge raw DDS, establish fixed geometry, then map.

3. Frame Ownership And Map Semantics

The important detail is unchanged: the bridge does not transform the corrected cloud into base_link. FAST-LIO receives LiDAR-frame data and therefore must be configured with the physical LiDAR pose in the IMU frame. The occupancy node then consumes FAST-LIO's registered cloud in camera_init and recenters a rolling map on the robot in cell-sized increments.

Editing Constraints

  • Do not switch the FAST-LIO extrinsic helper to base_link_pose_in_imu_frame() unless the cloud frame semantics change first.
  • Keep row_step-aware PointCloud2 decoding in any node that unpacks raw cloud buffers.
  • The occupancy node expects camera_init, base_link, and utlidar_lidar to be resolvable at runtime.
  • Log-odds occupancy parameters belong in config/occupancy_2d.yaml and launch-time parameter overrides, not in hard-coded per-site forks.
