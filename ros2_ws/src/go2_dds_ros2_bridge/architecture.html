GO2 DDS / ROS2 Architecture

This page shows how the physical GO2, the simulate_python runtime, and the ROS2 bridge package fit together. The main paths are the raw DDS transport, the bridge nodes that translate DDS into ROS2 topics and TF, and the optional KISS-ICP odometry branch.

Hardware DDS: domain 0 via enp108s0
Simulation DDS: domain 1 via wlo1
Raw topics: rt/odom, rt/utlidar/cloud
ROS2 outputs: /odom, /utlidar/time_corrected/cloud, /kiss/odom
KISS input: accumulated clouds with header-shifted point time
Physical robot, onboard sensors, Ethernet link
simulate_python scripts and MuJoCo-side runtime
go2_dds_ros2_bridge ROS2 executables
ROS2 topics consumed by RViz, SLAM, or other ROS tools
TF frames published into the ROS2 frame tree
Browser-only document: no build step, no external assets

1. End-to-End Map

The package does not import simulate_python. Both sides stay decoupled and meet only through shared DDS topics, and the KISS branch now runs on accumulated ROS clouds rather than one transport message at a time.

2. Hardware Path: GO2 to ROS2

On hardware, the ROS2 bridge listens to the same Unitree DDS traffic the robot publishes on the wired Ethernet path.

What matters here

  • The bridge executable chooses hardware defaults with DDS domain 0 and interface enp108s0.
  • clock_offset_bridge is the LiDAR cleanup step. It aligns timestamps to local ROS time before anything downstream uses the cloud.
  • odom_bridge is the low-friction path for robot odometry into standard ROS2 tools.
  • The LiDAR TF published here is base_link -> utlidar_lidar, so RViz and SLAM can place the cloud correctly.

3. Simulation Path: simulate_python to ROS2

In simulation, the contract is still DDS. The ROS2 bridge only cares that the expected topics exist; it does not need a Python import from the simulator.

Where the script interaction happens

  • unitree_mujoco.py and the control scripts initialize Unitree DDS channels for the simulator side.
  • GO2HardwareEnvironment creates EstimatedOdometryPublisher when velocity control is active.
  • That publisher writes DDS rt/odom, which the ROS2 odom_bridge can consume exactly like hardware odometry.
  • This symmetry is the key design choice: same bridge, same ROS2 outputs, different DDS producer.

4. ROS2 LiDAR and KISS-ICP Branch

KISS-ICP deliberately subscribes to the corrected ROS2 cloud instead of raw DDS so it can reuse the timestamp fix and LiDAR frame alignment from one place. Because the per-point time field resets every message, the node rebuilds a batch-global time axis from message headers before normalizing timestamps for deskew.

Why this split is useful

  • The timestamp correction and LiDAR mounting TF are handled once in the bridge.
  • kiss_odom_node stays focused on scan registration rather than DDS transport details.
  • The node accumulates multiple incoming clouds before each KISS registration because single-message registration was too unstable on the GO2 stream.
  • The published KISS pose is stamped with the newest message header in the accumulated batch, while deskew uses the oldest-to-newest per-point time ordering inside that batch.
  • --reset-after-registrations can periodically reinitialize KISS to bound local-map history while keeping the published pose continuous.
  • If you disable KISS-ICP, the rest of the bridge still works and ROS2 still has the corrected cloud and proprioceptive odometry.

5. TF View

Two odometry reference frames can exist at the same time: odom from the Unitree odometry path, and kiss_odom from LiDAR scan matching. They are intentionally separate trees.

Reading the frame tree

  • odom -> base_link comes from the odometry bridge.
  • base_link -> utlidar_lidar comes from the LiDAR bridge.
  • kiss_odom -> kiss_lidar is a separate branch produced by KISS-ICP.
  • kiss_lidar is virtual on purpose, so KISS does not compete with the bridge for ownership of utlidar_lidar.
  • Consumers choose which odometry frame they trust for their use case.
