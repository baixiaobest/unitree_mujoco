GO2 DDS / ROS2 FAST-LIO Architecture

This page reflects the current bridge design after removing the KISS-ICP and EKF fusion path. The active launch is now a direct DDS-to-FAST-LIO pipeline with optional rolling 2D occupancy mapping. Hardware and simulate_python remain symmetric at the transport layer: both publish the same DDS contract, and the bridge turns that into corrected ROS topics, static transforms, FAST-LIO inputs, a posture-triggered gravity leveling transform from camera_init_correct to camera_init, and an optional occupancy grid built in the corrected map frame.

1. End-to-End Runtime

The current launch is narrower and more explicit than the old fusion stack: correct the LiDAR clock, bridge the IMU, publish fixed transforms, run FAST-LIO, level the resulting map frame from gravity during stand_holding, and optionally derive a rolling occupancy grid from the corrected-frame cloud.

The package still ships standalone utilities such as odom_bridge, but the main launch no longer routes odometry through KISS-ICP or robot_localization.

What changed

  • The recommended entry point is now fast_lio.launch.py, not a fusion launch.
  • KISS-ICP is no longer installed or documented as part of the active package path.
  • robot_localization is no longer part of the package runtime dependency set.
  • fast_lio_frame_correction now levels FAST-LIO's camera_init under camera_init_correct using IMU gravity sampled during stand_holding.
  • That correction is roll and pitch only, and it also adjusts z so the robot body sits 0.4 m above the corrected ground plane.
  • Occupancy mapping is now the downstream consumer of the FAST-LIO registered cloud inside this package, but it filters in camera_init_correct after transforming points into the corrected map frame.
  • The design is closer to a pure transport-and-mapping stack: bridge raw DDS, establish fixed geometry, estimate, level, then map.

3. Frame Ownership, Correction, And Map Semantics

The important detail is unchanged: the bridge does not transform the corrected cloud into base_link. FAST-LIO receives LiDAR-frame data and therefore must be configured with the physical LiDAR pose in the IMU frame. The correction node then keeps FAST-LIO's camera_init as the child of a leveled camera_init_correct frame by solving roll and pitch from averaged IMU gravity and shifting z so the body sits at the configured standing height. The occupancy node consumes FAST-LIO's registered cloud, transforms points into camera_init_correct, applies z filtering there, and only then integrates the rolling map.

Editing Constraints

  • Do not switch the FAST-LIO extrinsic helper to base_link_pose_in_imu_frame() unless the cloud frame semantics change first.
  • Keep row_step-aware PointCloud2 decoding in any node that unpacks raw cloud buffers.
  • The correction node assumes the robot is in the posture-triggered stand hold and uses averaged IMU gravity to solve roll and pitch only; it does not try to estimate yaw.
  • The occupancy node now expects camera_init_correct, camera_init, base_link, and utlidar_lidar to be resolvable at runtime, and it pauses updates until the correction transform exists.
  • Log-odds occupancy parameters belong in config/occupancy_2d.yaml and launch-time parameter overrides, not in hard-coded per-site forks.

4. IMU Timestamp Reconstruction

The IMU bridge does not read a trustworthy absolute sensor timestamp from DDS. Instead it models the stream as 1 ms ticks, advances the next outgoing stamp by an integer number of ticks inferred from local receive-time spacing, and falls back to the current receive time when the reconstruction drifts by more than one tick. This is why the IMU path is stable enough for FAST-LIO, but it is still ultimately tied to the host ROS clock.

Why The Resync Exists

  • The bridge currently has cadence information but not a production-quality absolute IMU timebase from the Unitree DDS lowstate path.
  • Without the resync rule, receive-time jitter would slowly push reconstructed IMU stamps away from the actual arrival-time trend.
  • The max(1, round(receive_delta / 1 ms)) step prevents zero-tick repeats when messages arrive faster than expected.
  • The 1 ms error threshold is intentionally tight, so larger host-time or scheduling disturbances immediately snap the IMU clock model back onto local ROS time.
  • If you see repeated resync warnings, that is a sign to inspect host clock stability, callback latency, or the underlying DDS delivery cadence.

5. Navigation Pipeline: Goal to Velocity Command

Coordinate transform detail. The navigation node receives the goal in the map frame (camera_init_correct) and the robot pose from TF. It converts the world-frame displacement into the robot body frame with a yaw-only inverse rotation — identical to quat_rotate_inverse(yaw_quat(q), target_vec) in simulation — so the policy sees a body-relative goal vector regardless of robot heading. The z component uses a fixed configured height (goal_z, default 0.35 m) rather than the raw goal z, keeping the policy input near its training distribution. The heading error is wrapped into (−π, π] so the shortest angular distance is always presented. The 128-element scan from occupancy_scan is normalized to [0, 1] before concatenation.
